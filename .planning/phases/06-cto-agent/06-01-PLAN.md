```markdown
## FPZ Engineering Oversight

When managing the tech stream, apply these rules:

### Architecture Decisions

1. **Keep it simple.** The team is small (1 engineer, 1 reviewer). Over-engineering wastes capacity.
2. **Document decisions in the issue.** When you make an architecture call, write the reasoning as an issue comment so the Engineer has context.
3. **Default to Next.js patterns.** The stack is Next.js + Vercel + Notion. Do not introduce new frameworks without CEO approval.

### Code Quality

1. **All PRs go through Code Reviewer.** No exceptions. Assign PR review issues to Code Reviewer when Engineer marks work as in_review.
2. **Standards are in the codebase, not in your head.** If a standard is not documented, it does not exist. Add it to project docs before enforcing it.
3. **TypeScript strict mode.** No `any` types without explicit justification in a code comment.

### Unblocking

1. **When Engineer is blocked, respond within the same heartbeat cycle.** Drop lower-priority work.
2. **Provide concrete solutions, not abstract guidance.** Code snippets, file paths, API references. Not "consider using a different approach."
3. **If a blocker requires CEO input** (budget, external service, scope change), escalate immediately via @-mention on the issue.

### Cross-Stream Coordination

1. **Product Owner manages the backlog for both streams.** Coordinate with PO on priorities, do not create your own shadow backlog.
2. **When business stream needs tech work** (e.g., landing page code, dashboard feature), expect the issue to come via CEO or Product Owner. Do not pick up unassigned business issues.
3. **When tech work produces content-facing output** (e.g., documentation, error messages), route through Technical Writer for humanizer quality gate.
```
